# Raspberry Pi Local Deployment Design

## Goal

Deploy Fish Tournament on a Raspberry Pi 5 (8 GB) for one evening, with the game master, TV, and approximately 20 player phones connected to the same home network.

## Constraints

- The deployment must be minimal and quick to operate.
- No domain, public Internet exposure, TLS certificate, reverse proxy, Kubernetes, or external database.
- Players use a browser on their phones; no installation is required.
- The TV displays the read-only projector interface.
- The deployment must survive an application crash or Raspberry Pi reboot.
- Existing uncommitted application work must be preserved.

## Architecture

The application runs as one Docker Compose service on the Raspberry Pi. Docker publishes TCP port `8787` on every LAN interface. Express serves the compiled React application, the projector route, and the API from the same origin. SQLite persists in the existing named Docker volume `fish-data`.

```text
TV / game-master phone / player phones
                 |
          home Wi-Fi or Ethernet
                 |
       http://<raspberry-ip>:8787
                 |
         Docker: Fish Tournament
                 |
       named volume: fish-data
```

The Raspberry Pi should use Ethernet where possible and receive a stable DHCP reservation from the home router. The QR code generated by the projector view uses the browser origin, so opening the TV page through the Raspberry Pi LAN address produces a join URL that phones can reach.

## Access paths

- Main and game-master interface: `http://<raspberry-ip>:8787/`
- Projector setup: `http://<raspberry-ip>:8787/tv`
- Health check: `http://<raspberry-ip>:8787/api/health`

## Camera limitation

The player identity animation calls `getUserMedia`. Mobile browsers normally require a secure HTTPS context for camera access. Local HTTP therefore uses the application's existing no-camera visual fallback. Identity assignment and quiz gameplay remain functional; only the live camera preview is unavailable.

## Deployment flow

1. Copy the checked-out source tree to a dedicated directory on the Raspberry Pi without copying Git metadata, local build outputs, databases, or test artifacts.
2. Build the ARM64 image directly on the Raspberry Pi with Docker Compose.
3. Start the container with `restart: unless-stopped` and wait for its health check.
4. Verify the health endpoint locally and through the Raspberry Pi LAN address.
5. Open the projector route on the TV and scan the displayed QR code from at least one phone.

## Persistence, backup, and rollback

SQLite remains in `fish-data`. A backup command copies the SQLite database out of the volume into a timestamped file before replacement or upgrade. Rollback consists of restoring the previous source release or image and restarting Compose; database restoration is only required if the schema or data was damaged.

For this single-event deployment, automated scheduled backups, image registries, CI/CD deployment, monitoring stacks, and multi-host redundancy are explicitly out of scope.

## Failure handling

- Docker restarts the process after an application crash and after host reboot.
- The image health check detects an API that is not responding.
- Deployment scripts fail on command errors and verify prerequisites before modifying the running service.
- A failed new build does not stop the currently running container.
- The deployment replaces the running service only after the new image builds successfully.

## Validation

- Run the unit test suite and production build locally before transfer.
- Build the Docker image successfully.
- Confirm the container reaches `healthy` state.
- Confirm `/`, `/tv`, and `/api/health` respond over the LAN.
- Confirm a phone on the home Wi-Fi can join from the TV QR code.
- Reboot the Raspberry Pi once and confirm the service returns automatically.
